내 컴퓨터 안에서
나쁜 네트워크를 마음대로 만들어보세요

clumsy는 여러분의 PC를 오가는 네트워크 패킷을 붙잡아 일부러 지연시키고, 잃어버리고, 망가뜨리는 도구입니다. 서버나 공유기를 건드리지 않고도 "느린 와이파이", "끊기는 지하철 4G", "지구 반대편 서버" 같은 상황을 지금 이 컴퓨터에서 그대로 재현할 수 있습니다.

지금 시작하기 → 사용 예시부터 보기
🤔

왜 필요한가요?

"우리 집 와이파이에서는 잘 되는데 고객 환경에서는 이상해요" — 이런 문제는 좋은 네트워크에서는 절대 재현되지 않습니다. clumsy는 나쁜 네트워크를 원할 때 원하는 만큼 만들어 줍니다.

🧰

무엇을 할 수 있나요?

지연(Lag·Jitter), 손실(Drop·Burst Loss·Blackout), 변형(Duplicate·Tamper·Corrupt), 대역폭 제한, 강제 연결 끊기까지 총 12가지 효과를 조합해서 켤 수 있습니다.

🖱️

어떻게 조작하나요?

화면 프로그램(GUI)이 따로 없습니다. 브라우저로 여는 웹 대시보드 하나로 클릭만으로 조작하거나, 명령어(CLI)·REST API로 자동화할 수 있습니다.

소개

clumsy는 정확히 무슨 일을 하나요?

한 줄로 말하면: 내 컴퓨터가 보내고 받는 패킷을 붙잡아서 일부러 나쁜 상태로 만든 뒤 다시 보내는 프로그램입니다. 실제 서버·공유기·통신사망은 전혀 건드리지 않으므로, 다른 사람에게 영향을 주지 않고 오직 내 PC의 트래픽만 대상으로 안전하게 실험할 수 있습니다.

클라이언트에 설치할까요, 서버에 설치할까요?

정답: 둘 중 어느 한쪽에만 설치하면 됩니다. clumsy는 자기가 설치된 그 PC를 오가는 트래픽만 가로챕니다 — 상대방 컴퓨터에는 아무것도 설치하거나 손댈 필요가 없습니다.

가장 흔한 방법 🖥️

클라이언트(내 PC)에 설치

"나쁜 네트워크를 쓰는 유저"의 입장을 재현합니다. 서버는 정상이고, 내 컴퓨터가 보내고 받는 패킷만 지연·손실시킵니다. 이 가이드의 시나리오 대부분이 이 방식이며, 개인 개발자가 가장 쉽게 시작할 수 있는 방법입니다.

고급 사용 🖧

서버에 설치

서버 쪽 회선이 느리거나 혼잡할 때 여러 클라이언트가 어떻게 반응하는지 보고 싶을 때 씁니다. 서버가 Windows이고 거기에 관리자 권한으로 접근할 수 있어야 합니다. 서버가 Linux라면 docs/LINUX.md의 Linux 빌드(NFQUEUE 기반)를 대신 씁니다.

☝️

양쪽에 동시에 설치할 필요는 거의 없습니다. 한쪽 PC에서도 Inbound(수신)·Outbound(송신)를 모두 독립적으로 제어할 수 있어서, 클라이언트↔서버 연결 하나에 대한 지연·손실 효과는 어느 한쪽에만 설치해도 충분합니다. 둘 다 필요한 경우는 "클라이언트는 나쁜 와이파이를 쓰고, 동시에 서버도 회선이 혼잡하다"처럼 서로 다른 문제를 동시에 재현하고 싶은 특수한 상황뿐입니다.

📎

같은 PC에서 서버·클라이언트를 함께 띄워 테스트한다면(로컬 개발), 그 한 대에만 clumsy를 설치하고 loopback 필터 (udp and outbound and loopback)를 쓰면 됩니다 — 시나리오: 로컬 개발환경 테스트 참고. 단, 서버를 WSL2 안에서 돌린다면 주의하세요 — WSL2는 별도의 네트워크 네임스페이스를 쓰기 때문에 Windows 호스트에 설치한 clumsy로는 WSL2 안에서 도는 서버의 트래픽을 건드릴 수 없습니다.

💡

GUI 창이 없다는 점만 기억하세요. clumsy를 실행하면 검은 콘솔 창 하나가 뜨는데, 여기서 조작하는 게 아니라 콘솔에 적힌 주소를 브라우저로 열어서 웹 대시보드로 조작합니다. 아래 "시작하기"에서 바로 보여드릴게요.

시작하기

3분이면 첫 번째 지연을 만들 수 있습니다

Windows 7/8/10/11(64비트)에서 동작하며, 네트워크 드라이버를 다루는 프로그램이라 관리자 권한이 꼭 필요합니다. 별도 설치 과정 없이 clumsy.exe 하나만 실행하면 됩니다.

  1. ① 관리자 권한으로 콘솔을 연다

    시작 메뉴에서 "명령 프롬프트" 또는 "PowerShell"을 관리자 권한으로 실행합니다. clumsy는 패킷을 가로채는 드라이버(WinDivert)를 로드하기 때문에 일반 권한으로는 캡처를 시작할 수 없습니다.

  2. ② clumsy.exe 를 실행한다

    아무 옵션 없이 실행하면 캡처는 시작하지 않고 대시보드만 띄운 대기 상태로 켜집니다. 아래처럼 배너가 출력됩니다.

    clumsy 0.4 - console + web network condition simulator
    Administrator : yes
    Web dashboard : http://127.0.0.1:8080/
    Named Pipe : \\.\pipe\clumsy
    Presets : 34 loaded
    Profiles : 2 loaded
    Press Ctrl+C to quit.
  3. ③ 배너에 적힌 주소를 브라우저로 연다

    기본 주소는 http://127.0.0.1:8080/ 입니다. 내 컴퓨터 안에서만 열리는 로컬 주소라 인터넷 연결이 없어도 동작하고, 다른 사람은 접근할 수 없습니다.

  4. ④ 대시보드에서 필터를 정하고 Start를 누른다

    어떤 패킷을 붙잡을지(필터)를 정하고 Start를 누르면 그 순간부터 캡처가 시작됩니다. 자세한 방법은 바로 아래 "대시보드" 섹션에서 이어집니다.

  5. ⑤ 끝났으면 Ctrl+C

    콘솔 창에서 Ctrl+C를 누르면 안전하게 종료됩니다. clumsy는 한 번에 하나만 실행할 수 있어서, 이미 켜져 있는 상태로 다시 실행하면 새 인스턴스가 자동으로 종료됩니다.

⚠️

관리자 권한 없이 실행하면? 프로그램이 꺼지지는 않고 경고만 띄운 채 대시보드는 계속 뜹니다. 다만 이 상태에서 Start를 눌러도 clumsy needs Administrator rights to open the WinDivert driver. 오류가 나며 캡처가 시작되지 않습니다. 명령줄에 --elevate on을 붙이면 UAC 창을 띄워 자동으로 관리자 권한으로 재실행합니다.

명령어로 바로 시작하고 싶다면

대시보드를 거치지 않고, 실행과 동시에 조건을 지정할 수도 있습니다. 아래는 UDP 송신 패킷에 100ms 지연과 5% 손실을 동시에 거는 예시입니다.

clumsy.exe --filter "udp and outbound" --lag on --lag-time 100 --drop on --drop-chance 5.0

이 명령어의 각 부분이 무슨 뜻인지는 필터 섹션과 CLI 섹션에서 하나씩 풀어서 설명합니다. 지금은 "이런 식으로 한 줄로도 켤 수 있구나" 정도만 기억해 두세요.

필터

"어떤 패킷을 건드릴지" 정하기

필터는 clumsy가 가로챌 패킷의 조건입니다. 필터에 걸리지 않은 패킷은 그냥 평소처럼 지나가고, 필터에 걸린 패킷만 아래에서 켠 기능(지연·손실 등)의 대상이 됩니다. WinDivert라는 Windows 네트워크 드라이버의 필터 문법을 그대로 사용합니다.

자주 쓰는 필터

udpUDP 통신만 (대부분의 온라인 게임)
tcpTCP 통신만 (웹, 대부분의 앱 서버 통신)
outbound내가 보내는 패킷만
inbound내가 받는 패킷만
udp and (udp.DstPort == 7777 or udp.SrcPort == 7777)7777 포트를 쓰는 UDP만 (게임 서버 포트 지정)
udp and outbound and loopback같은 PC 안에서 도는 서버·클라이언트 테스트용
⚠️

localhost(loopback) 테스트 시 주의 — 같은 PC에서 서버와 클라이언트를 함께 띄워 테스트할 때는 반드시 outbound 조건을 포함해야 합니다. inbound and loopback 조합은 동작하지 않습니다. 대시보드 Presets에서 localhost ipv4 udp를 고르면 올바른 형태(udp and outbound and loopback)가 자동으로 채워집니다.

필터 문법을 몰라도 괜찮아요

대시보드의 Filter builder를 펼치면 프로토콜(TCP/UDP/ICMP)·방향(송신/수신)·포트·상대 IP·loopback 여부를 드롭다운으로 고르는 것만으로 필터 문구가 자동으로 만들어집니다. 만들어진 문구는 Save as preset으로 이름을 붙여 저장해두면 다음에는 드롭다운에서 바로 선택할 수 있습니다.

프로세스 이름으로만 좁히기

Process 입력란에 실행 파일 이름(예: game.exe)을 넣으면 그 프로그램이 쓰는 포트만 자동으로 찾아 필터에 더합니다. 단, 이 포트는 Start를 누르는 순간에 한 번만 조사하므로, 게임을 먼저 켜서 서버에 접속한 뒤에 clumsy를 Start 하는 순서를 권장합니다.

clumsy.exe --filter "udp" --process game.exe --lag on --lag-time 100
기능(모듈)

12가지 효과, 필요한 만큼만 켜세요

clumsy.exe --filter "udp and outbound" --lag on --lag-time 150

이럴 때 — 실제 인터넷처럼 지연이 불규칙한 환경, 랙 보상(lag compensation) 로직 테스트. pareto는 "가끔 크게 튀는" 혼잡망을 재현합니다.
clumsy.exe --filter "udp and outbound" --jitter on --jitter-min 30 --jitter-max 200

일정 확률로 패킷이 사라짐

손실

Drop 패킷 드롭

패킷마다 독립적인 확률로 그냥 버립니다(동전 던지기와 같은 방식). 손실이 골고루 흩어져서 발생합니다.

파라미터설명기본값범위
drop-chance드롭 확률10.0%0~100%
이럴 때 — 재전송·손실 복구 로직 검증. 아래 Burst Loss와 달리 손실이 몰리지 않고 고르게 퍼집니다.
clumsy.exe --filter "udp and outbound" --drop on --drop-chance 5.0

손실이 연속으로 몰려서 발생 (Good/Bad 상태)

손실

Burst Loss 연속 손실

Good(평소)·Bad(버스트) 두 상태를 오가는 모델(Gilbert-Elliott)입니다. 한번 Bad에 들어가면 몇 개 패킷이 연속으로 사라집니다 — "손실이 몰려서" 오는 무선 환경을 더 현실적으로 재현합니다.

파라미터설명기본값
burstloss-goodGood 상태 드롭 확률2.0%
burstloss-badBad 상태 드롭 확률80.0%
burstloss-gbGood→Bad 전환 확률5.0%
burstloss-bgBad→Good 전환 확률20.0%
이럴 때 — 전파 간섭, 터널 진입처럼 짧은 구간 동안 연속으로 끊기는 상황. Drop 10%와 Burst Loss 10%는 총 손실률이 같아도 앱이 겪는 체감은 완전히 다릅니다.
clumsy.exe --filter "udp and outbound" --burstloss on

페이로드(데이터 부분)의 1/4 구간을 XOR 패턴으로 의도적으로 덮어씁니다. 어디를 건드릴지 위치를 고를 수 있습니다.

파라미터설명기본값범위

좁은 구간에서 속도가 줄어들며 통과

연결

Bandwidth 대역폭 제한

초당 전송량(KB/s)을 제한합니다. 한도를 넘는 패킷은 버리지 않고 큐에 쌓아두었다가 순서대로 지연 전송합니다.

파라미터설명기본값범위
bandwidth-bandwidth대역폭 상한10 KB/s0~99999 KB/s
이럴 때 — 저속 모바일 회선·혼잡망 재현. 패킷을 보존한 채 속도만 줄이므로 TCP 흐름 제어·재전송 로직 테스트에 Drop보다 적합합니다.
⚠️

토큰 버킷은 최대 64KB(또는 제한×2초)만큼 가득 찬 채로 시작합니다. 그래서 짧은 테스트에서는 처음 얼마간 "제한이 안 걸리는 것처럼" 보일 수 있습니다 — 정상입니다.

clumsy.exe --filter "udp and outbound" --bandwidth on --bandwidth-bandwidth 500

🎮 해외 게임 서버 핑 재현 ▸Lag

상황 — 게임 서버가 해외에 있어서 항상 150ms 지연이 발생하는 상황을 미리 재현하고 싶다.

필터Lag

확인 포인트 — 게임을 켜고 인게임 핑 표시가 150ms 전후로 고정되는지 확인합니다.

clumsy.exe --filter "udp and outbound" --lag on --lag-time 150
📶 불안정한 Wi-Fi 재현 ▸Jitter + Drop

상황 — 신호가 약한 Wi-Fi처럼 지연이 들쭉날쭉하고 가끔 패킷이 사라지는 환경.

필터JitterDrop
udp and outboundON, Min=30ms Max=200msON, Chance=3.0%

확인 포인트 — 응답 시간이 불규칙해지고, 100개 중 약 3개 패킷이 사라지는 상황에서 앱이 자연스럽게 버티는지 확인합니다.

clumsy.exe --filter "udp and outbound" --jitter on --jitter-min 30 --jitter-max 200 --drop on --drop-chance 3.0
📱 모바일 4G / 3G 환경 재현 ▸Lag+Jitter+Drop+Bandwidth

상황 — 스마트폰으로 4G 또는 지하철 3G 환경에서 앱을 쓰는 유저를 시뮬레이션.

확인 포인트 — 로딩 스피너, 재시도 UI, 타임아웃 문구가 각 등급에서 적절히 나타나는지 확인합니다.

clumsy.exe --filter "udp and outbound" --lag on --lag-time 150 --jitter on --jitter-min 50 --jitter-max 300 --drop on --drop-chance 8.0 --bandwidth on --bandwidth-bandwidth 500
🛰️ 위성 통신 / 극한 지연 재현 ▸Lag+Jitter+Drop

상황 — 위성 인터넷처럼 지연이 극단적으로 크지만 그 자체는 비교적 일정한 환경.

필터LagJitterDrop
udp and outboundON, 500msON, 20~80msON, 1.0%

확인 포인트 — 500ms+ RTT에서 실시간 상호작용이 사실상 불가능해집니다. 타임아웃·연결 끊김 처리를 어떻게 하는지 관찰합니다.

clumsy.exe --filter "udp and outbound" --lag on --lag-time 500 --jitter on --jitter-min 20 --jitter-max 80 --drop on --drop-chance 1.0

상황 — 지하철 터널처럼 짧은 구간 동안 연속으로 패킷이 사라지는 상황. Drop만 쓰면 손실이 흩어져서 이 느낌이 안 납니다.

clumsy.exe --filter "udp and outbound" --burstloss on --burstloss-good 1.0 --burstloss-bad 70.0 --burstloss-gb 10.0 --burstloss-bg 40.0

🏠 로컬 개발환경(localhost) 테스트 ▸Lag + Drop

상황 — 같은 PC에서 클라이언트와 서버를 함께 띄우고 네트워크 조건을 테스트하고 싶다.

필터LagDrop
udp and outbound and loopbackON, 80msON, 2.0%

🤖 CI/CD 자동화 테스트 ▸시나리오 파일

상황 — 빌드 파이프라인에서 네트워크 조건을 단계적으로 바꿔가며 자동 테스트를 돌리고 싶다.

가장 간단한 방법은 시나리오 파일 하나로 전체 흐름을 정의하는 것입니다. "몇 초 시점에 어떤 값으로 바꿔라"를 배열로 적습니다.

[

  { "at": 30, "lag-time": 200, "jitter": true, "jitter-min": 50, "jitter-max": 300,

clumsy.exe --filter "udp and outbound" --scenario ci_scenario.json --timeout 90

확인 포인트 — 시나리오 파일만 버전 관리하면 QA 팀 누구나 동일한 조건을 재현할 수 있습니다. REST API나 Named Pipe로 실시간 전환하는 방법은 자동화 섹션에서 다룹니다.

🧪 패킷 변조·퍼징 테스트 ▸Tamper

상황 — 게임 패킷의 헤더나 시퀀스 번호가 손상됐을 때 서버가 올바르게 에러 처리하는지 확인하고 싶다.

목적PositionChance
시퀀스 번호 손상(헤더 타격)0 (Front)5.0%
예측 불가 손상(퍼징)3 (Random)10.0%

확인 포인트 — 대부분의 게임 UDP 패킷은 헤더가 앞쪽에 있으므로 Front 위치를 손상시키면 잘못된 패킷 타입·시퀀스 번호를 받은 서버의 처리를 검증할 수 있습니다. Random은 예상치 못한 파싱 오류·크래시를 찾는 퍼징에 가깝습니다.

clumsy.exe --filter "udp and outbound" --tamper on --tamper-chance 5.0 --tamper-position 0 --tamper-checksum on
🔁 UDP 중복 패킷 처리 테스트 ▸Duplicate

상황 — 네트워크 장비의 재전송으로 같은 패킷이 두 번 오는 경우, 서버가 중복을 올바르게 무시하는지 확인하고 싶다.

전역 옵션

옵션설명

--process <이름>특정 프로세스(예: game.exe)의 트래픽만 필터링.
--timeout <초>지정 시간 후 자동 종료. 테스트 스크립트에 유용.
--profile <이름>profiles.json에 저장해둔 프로파일을 불러와 적용.
--scenario <파일>시나리오 JSON 파일을 로드해 시작과 동시에 재생.

예시 모음

# 게임 서버(7777 포트) UDP에 100ms 지연 + 3% 드롭
clumsy.exe --filter "udp and (udp.DstPort==7777 or udp.SrcPort==7777)" --lag on --lag-time 100 --drop on --drop-chance 3.0

# 30초만 실행 후 자동 종료
clumsy.exe --filter "udp and outbound" --lag on --lag-time 200 --timeout 30

# 통계를 CSV로 기록하며 60초 테스트
clumsy.exe --filter "udp and outbound" --drop on --drop-chance 5.0 --stats-log result.csv --timeout 60

# 대시보드 없이 완전 헤드리스로 실행 (서버/컨테이너용)
clumsy.exe --filter "udp and outbound" --drop on --drop-chance 5.0 --web off --timeout 30

자동화

REST API로 원격 조종하기

대시보드가 클릭하는 모든 동작은 결국 REST API 호출입니다. CI 파이프라인, 자동화 스크립트, 다른 프로그램에서도 똑같이 clumsy를 제어할 수 있습니다. 로컬호스트(127.0.0.1)로 접속할 때는 인증이 필요 없습니다. --web-bind로 외부에 열면 X-Clumsy-Token 헤더 또는 ?token=이 필요합니다.

엔드포인트설명
GET/api/health생존 확인 (인증 불필요, CI 헬스체크용)
GET/api/status캡처 상태, 필터, 마지막 메시지
GET/api/modules모듈 전체 상태 + 파라미터 + 폼 메타데이터
GET/api/stats실시간 통계(캡처/전송/버퍼/지연 분위수)
GET/api/streamServer-Sent Events, 200ms 주기로 통계 push
GET/metricsPrometheus 텍스트 노출 형식 (인증 불필요)
POST/api/filter필터 설정 후 캡처 시작
POST/api/stop캡처 중지
POST/api/modules/{name}모듈 활성화/파라미터 변경
POST/api/apply여러 모듈을 저장 없이 한 번에 설정
POST/api/scenario/start시나리오 재생 시작

curl 예시

# 캡처 시작
curl -X POST http://127.0.0.1:8080/api/filter -H "Content-Type: application/json" -d "{\"filter\":\"udp and outbound\"}"

# lag 켜고 지연 200ms로 설정
curl -X POST http://127.0.0.1:8080/api/modules/lag -H "Content-Type: application/json" -d "{\"enabled\":true,\"lag-time\":200}"

# 여러 모듈을 한 번에 설정
curl -X POST http://127.0.0.1:8080/api/apply -H "Content-Type: application/json" -d "{\"lag\":true,\"lag-time\":200,\"drop\":true,\"drop-chance\":5.0}"

# 캡처 중지 후 통계 확인
curl -X POST http://127.0.0.1:8080/api/stop
curl http://127.0.0.1:8080/api/stats

Python으로 실시간 스트림 구독

import requests, json

with requests.get("http://127.0.0.1:8080/api/stream", stream=True) as r:
    for line in r.iter_lines(decode_unicode=True):
        if line and line.startswith("data: "):
            stats = json.loads(line[6:])
            print(stats["captured"], stats["sent"])
🔧

Named Pipe API도 있습니다. Windows에서는 \\.\pipe\clumsy로 JSON 요청 1개 → JSON 응답 1개를 주고받는 방식입니다. REST와 내부적으로 완전히 같은 처리 로직(controlapi.cpp)을 공유하므로 두 방식은 절대 동작이 갈라지지 않습니다. 기존에 Named Pipe로 만들어 둔 자동화 스크립트가 있다면 수정 없이 그대로 씁니다.

문제 해결

자주 묻는 질문

관리자 권한이 필요하다는 오류가 나요

clumsy는 네트워크 드라이버(WinDivert)를 로드해야 패킷을 가로챌 수 있습니다. 콘솔(명령 프롬프트/PowerShell)을 관리자 권한으로 다시 실행하세요. 매번 수동으로 하기 번거롭다면 --elevate on을 붙이면 UAC 창을 자동으로 띄워줍니다.

필터를 넣고 Start를 눌렀는데 아무 효과가 없어요

가장 흔한 원인 두 가지입니다. ① localhost 테스트인데 outbound 조건이 빠졌는지 확인하세요(inbound and loopback은 동작하지 않습니다). ② 모듈은 켰지만 Inbound/Outbound 체크박스가 실제 트래픽 방향과 반대로 되어 있지 않은지 확인하세요.

이미 실행 중이라며 꺼져요

clumsy는 한 번에 하나의 인스턴스만 실행할 수 있습니다. 새로 실행하면 기존에 떠 있던 인스턴스가 자동으로 종료됩니다. 작업 표시줄이나 작업 관리자에서 기존 콘솔 창이 남아있는지 확인하세요.

Bandwidth를 낮게 걸었는데 처음엔 제한이 안 걸리는 것 같아요

정상입니다. 대역폭 제한은 토큰 버킷 방식이라 최대 64KB(또는 제한값×2초 중 큰 값)만큼 가득 찬 상태로 시작합니다. 그래서 짧은 테스트에서는 초반 트래픽이 그냥 통과한 것처럼 보입니다 — 테스트를 좀 더 길게(또는 더 많은 데이터로) 돌려보세요.

브라우저에서 대시보드가 안 열려요

콘솔에 출력된 배너의 주소(기본 http://127.0.0.1:8080/)를 그대로 입력했는지 확인하세요. 다른 프로그램이 8080 포트를 이미 쓰고 있다면 --web-port 9090처럼 다른 포트를 지정하면 됩니다.

다른 PC에서 원격으로 이 clumsy 인스턴스를 제어하고 싶어요

--web-bind 0.0.0.0 --web-token 원하는토큰으로 실행하면 외부에서 접속할 수 있습니다. 외부 바인딩 시에는 토큰이 강제되므로, 요청마다 X-Clumsy-Token 헤더 또는 ?token= 쿼리스트링을 붙여야 합니다. 신뢰할 수 있는 테스트망에서만 사용하세요.

Set TCP RST를 켰는데 아무 일도 안 일어나요

Reset 모듈은 TCP 전용입니다. UDP 트래픽에는 효과가 없습니다. 필터가 tcp 조건을 포함하는지, 대상 서비스가 실제로 TCP를 쓰는지 확인하세요.
