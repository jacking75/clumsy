A beginner's guide to clumsy

Create a bad network
right inside your own computer

clumsy grabs the network packets going in and out of your PC and deliberately delays, loses and mangles them. Without touching a server or a router, you can reproduce "slow Wi-Fi", "patchy 4G on the subway" or "a server on the other side of the planet" right here on this machine.

Get started → See usage examples first
🤔

Why would I need it?

"It works fine on my home Wi-Fi, but customers say it acts up" — problems like this never show up on a good network. clumsy gives you a bad network whenever you want it, exactly as bad as you want it.

🧰

What can it do?

Delay (Lag, Jitter), loss (Drop, Burst Loss, Blackout), mutation (Duplicate, Tamper, Corrupt), bandwidth caps and forced disconnects — 12 effects in total that you can switch on in any combination.

🖱️

How do I control it?

There is no separate desktop app (GUI). You click your way through a single web dashboard in your browser, or automate everything from the command line (CLI) or the REST API.

Intro

So what exactly does clumsy do?

In one sentence: it catches the packets your computer sends and receives, makes them worse on purpose, and sends them on. It never touches real servers, routers or your carrier's network, so it affects nobody else — you experiment safely on your own PC's traffic only.

Install it on the client or on the server?

Short answer: on just one of them. clumsy only intercepts traffic going in and out of the PC it runs on — you don't need to install or change anything on the other machine.

Most common 🖥️

On the client (your PC)

Reproduces the experience of "a user on a bad network". The server is healthy; only the packets your computer sends and receives get delayed or lost. Most scenarios in this guide work this way, and it is the easiest place for an individual developer to start.

Advanced 🖧

On the server

Use this when you want to see how many clients react when the server's own link is slow or congested. The server must run Windows and you need Administrator access to it. If the server runs Linux, use the Linux build (NFQUEUE-based) described in docs/LINUX.md (Korean) instead.

☝️

You almost never need it on both sides. A single PC can control Inbound (receive) and Outbound (send) independently, so for delay or loss on one client↔server connection, installing it on either side is enough. You only need both when you want to reproduce two different problems at once — for example "the client is on bad Wi-Fi, and at the same time the server's link is congested".

📎

If you run the server and the client on the same PC (local development), install clumsy on that one machine and use a loopback filter (udp and outbound and loopback) — see Scenarios: local development testing. Be careful if your server runs inside WSL2, though: WSL2 uses its own network namespace, so clumsy installed on the Windows host cannot touch the traffic of a server running inside WSL2.

💡

Just remember there is no GUI window. When you run clumsy, a black console window appears. You don't operate it there — you open the address printed in the console in your browser and work in the web dashboard. "Get started" below shows you how.

Get started

Your first delay in three minutes

clumsy runs on Windows 7/8/10/11 (64-bit). Because it works with a network driver, it requires Administrator rights. There is no installer: you just run clumsy.exe.

  1. ① Open a console as Administrator

    From the Start menu, run "Command Prompt" or "PowerShell" as administrator. clumsy loads a packet-intercepting driver (WinDivert), so it cannot start capturing with normal rights.

  2. ② Run clumsy.exe

    Run without any options, it does not start capturing — it just brings up the dashboard and waits. You will see a banner like this.

    clumsy 0.4 - console + web network condition simulator
    Administrator : yes
    Web dashboard : http://127.0.0.1:8080/
    Named Pipe : \\.\pipe\clumsy
    Presets : 34 loaded
    Profiles : 2 loaded
    Press Ctrl+C to quit.
  3. ③ Open the address from the banner in your browser

    The default address is http://127.0.0.1:8080/. It is a local address that only opens on your own computer, so it works without an internet connection and nobody else can reach it.

  4. ④ Pick a filter in the dashboard and press Start

    Choose which packets to catch (the filter) and press Start; capturing begins right then. The "Dashboard" section just below goes into the details.

  5. ⑤ Press Ctrl+C when you are done

    Press Ctrl+C in the console window to shut down safely. You can run several clumsy instances at once (say, one per client with different conditions), but each needs its own --web-port and --pipe-name; launched again with the same ones, the new instance exits on its own.

⚠️

What if I run it without Administrator rights? The program doesn't quit; it prints a warning and the dashboard still comes up. But pressing Start in this state fails with clumsy needs Administrator rights to open the WinDivert driver. and no capture starts. Add --elevate on to the command line and clumsy will show a UAC prompt and relaunch itself as Administrator.

If you want to start straight from the command line

You can skip the dashboard and set the conditions as you launch. This example adds 100 ms of delay and 5% loss to outgoing UDP packets at the same time.

clumsy.exe --filter "udp and outbound" --lag on --lag-time 100 --drop on --drop-chance 5.0

Each part of this command is explained one by one in the Filters section and the CLI section. For now, just remember that "you can turn it all on in a single line like this".

Filters

Choosing "which packets to mess with"

A filter is the condition for the packets clumsy intercepts. Packets that don't match go through as usual; only matching packets are subjected to the effects you switch on below (delay, loss and so on). clumsy uses the filter syntax of WinDivert, the Windows network driver, as-is.

Common filters

udpUDP traffic only (most online games)
tcpTCP traffic only (the web, most app-server traffic)
outboundOnly packets you send
inboundOnly packets you receive
udp and (udp.DstPort == 7777 or udp.SrcPort == 7777)Only UDP on port 7777 (pin it to a game server port)
udp and outbound and loopbackFor testing a server and client running on the same PC
⚠️

Careful when testing localhost (loopback) — when the server and client run together on the same PC, you must include the outbound condition. The combination inbound and loopback does not work. Pick localhost ipv4 udp from the dashboard Presets and the correct form (udp and outbound and loopback) is filled in for you.

You don't need to know the filter syntax

Open the dashboard's Filter builder and just pick the protocol (TCP/UDP/ICMP), direction (send/receive), port, remote IP and loopback from dropdowns; the filter text is generated for you. Save the result under a name with Save as preset and next time you can pick it straight from the dropdown.

Narrowing it down to one process

Put an executable name (e.g. game.exe) in the Process box and clumsy finds the ports that program uses and adds them to the filter. These ports are looked up only once, at the moment you press Start, so the recommended order is: launch the game, connect to the server, and then Start clumsy.

clumsy.exe --filter "udp" --process game.exe --lag on --lag-time 100
Effects (modules)

12 effects — switch on only what you need

Each effect is an independent on/off switch. You can turn on several at once, and every one of them can be applied to Inbound (receive) and Outbound (send) separately. The animations below show the feel of each effect, not real timing — see the tables for exact values.

🖥️
🌐

Every packet arrives equally late

Delay

Lag fixed delay

Holds every packet for a set time (ms) before sending it. Since the delay is always the same, it produces a "steady ping".

ParameterMeaningDefaultRange
lag-timeDelay50ms0–15000ms
Use it when — you want to reproduce something that is "always equally far away", like an overseas server.
clumsy.exe --filter "udp and outbound" --lag on --lag-time 150
🖥️
🌐

Packets arrive unevenly, each at its own pace

Delay

Jitter variable delay

Gives each packet a random delay between Min and Max. Because every packet is delayed by a different amount, arrival order can get shuffled naturally.

ParameterMeaningDefaultRange
jitter-minMinimum delay20ms0–5000ms
jitter-maxMaximum delay100ms0–5000ms
jitter-distDistribution shapeuniformuniform / normal / pareto
Use it when — you need irregular latency like the real internet, or want to test lag compensation. pareto reproduces a congested network that "occasionally spikes hard".
clumsy.exe --filter "udp and outbound" --jitter on --jitter-min 30 --jitter-max 200
🖥️
🌐

Packets vanish at a set probability

Loss

Drop packet drop

Simply throws each packet away with an independent probability (like a coin toss). Losses are spread out evenly.

ParameterMeaningDefaultRange
drop-chanceDrop probability10.0%0–100%
Use it when — verifying retransmission and loss-recovery logic. Unlike Burst Loss below, losses don't cluster; they are spread evenly.
clumsy.exe --filter "udp and outbound" --drop on --drop-chance 5.0

Losses come in clusters (Good/Bad states)

Loss

Burst Loss clustered loss

A model that switches between two states, Good (normal) and Bad (burst) — the Gilbert-Elliott model. Once it enters Bad, several packets in a row disappear — a more realistic picture of wireless links, where "losses come in bunches".

ParameterMeaningDefault
burstloss-goodDrop probability in Good state2.0%
burstloss-badDrop probability in Bad state80.0%
burstloss-gbGood→Bad transition probability5.0%
burstloss-bgBad→Good transition probability20.0%
Use it when — the link drops out repeatedly for a short stretch, as with radio interference or entering a tunnel. Drop 10% and Burst Loss 10% may have the same total loss rate, but the app experiences them completely differently.
clumsy.exe --filter "udp and outbound" --burstloss on
🖥️
🌐
🚫 Connection lost

Cuts everything off periodically, then recovers

Loss

Blackout outage

After a normal period (Gap), it blocks every packet completely for a set time (Duration). This cycle repeats over and over.

ParameterMeaningDefaultRange
blackout-durationHow long each outage lasts3000ms100–60000ms
blackout-gapNormal time between outages15000ms1000–300000ms
blackout-triggerTrigger now (button)—Click to start/cancel an outage immediately
Use it when — testing client reconnect logic, timeout handling and session recovery code. It drops immediately with no buffering, which is what sets it apart from Throttle below.
clumsy.exe --filter "udp and outbound" --blackout on --blackout-duration 3000 --blackout-gap 20000
🖥️
🌐

Holds packets briefly, then sends them all in one burst

Loss

Throttle temporary hold

Randomly pauses sending for a moment and piles packets up in a buffer. When the time is up it sends them all at once (a burst) or, depending on the setting, throws them all away.

ParameterMeaningDefaultRange
throttle-chanceProbability of starting a hold10.0%0–100%
throttle-frameHow long a hold lasts30ms0–1000ms
throttle-dropDiscard held packets?OFF (send in a burst)ON discards them
Use it when — reproducing network gear that briefly floods or stalls traffic.
clumsy.exe --filter "udp and outbound" --throttle on --throttle-chance 10.0 --throttle-frame 50
🖥️
🌐

A packet is copied on the way and arrives twice

Mutation

Duplicate packet copies

Packets hit by the probability are copied and sent back to back the given number of times. The same content arrives several times.

ParameterMeaningDefaultRange
duplicate-chanceProbability of duplicating10.0%0–100%
duplicate-countNumber of copies (including the original)22–50
Use it when — verifying that server and client correctly ignore duplicates when the same packet arrives twice, especially in UDP games.
clumsy.exe --filter "udp and outbound" --duplicate on --duplicate-count 2 --duplicate-chance 20.0
🖥️
🌐
123

Packets arrive in a different order than they were sent

Mutation

Out of Order reordering

Collects packets in an internal buffer for a moment, and when the buffer is full or the oldest packet has waited past the limit, releases them all at once in random order.

ParameterMeaningDefaultRange
ood-chanceProbability of catching a packet in the buffer10.0%0–100%
ood-bufferMaximum packets held52–50
ood-delayMaximum hold time200ms10–2000ms
Use it when — verifying UDP sequence-number handling and packet reassembly logic. The difference: Jitter shuffles naturally, while Out of Order deliberately collects and shuffles.
clumsy.exe --filter "udp and outbound" --ood on --ood-chance 15.0 --ood-buffer 8 --ood-delay 300
🖥️
🌐

Content gets damaged on the way and arrives that way

Mutation

Tamper payload tampering

Deliberately overwrites a quarter of the payload (the data part) with an XOR pattern. You can choose where it strikes.

ParameterMeaningDefaultRange
tamper-chanceTamper probability10.0%0–100%
tamper-positionWhere to tamper1 (Center)0=Front 1=Center 2=Back 3=Random
tamper-checksumRecompute checksum after tamperingON—
Use it when — verifying that the server handles errors properly when a game packet's header or sequence number is damaged. With Redo checksum off, the OS may simply drop the packet, so leave it on if you want the damaged data to reach the application.
clumsy.exe --filter "udp and outbound" --tamper on --tamper-chance 5.0 --tamper-position 0
🖥️
🌐

Bits flip sporadically along the way

Mutation

Corrupt bit errors

Flips each bit of the payload independently with a very small probability. If Tamper is "deliberate manipulation", Corrupt is closer to the sporadic noise that really happens on Wi-Fi and cellular links.

ParameterMeaningDefaultRange
corrupt-chanceProbability of damaging a packet10%0–100%
corrupt-berPer-bit flip probability (ppm)1000–1,000,000
corrupt-checksumRecompute checksum after damageON—
Use it when — checking what the app does when it meets partly damaged data on a wireless link. 100 ppm is roughly one flipped bit every 1250 bytes.
clumsy.exe --filter "udp and outbound" --corrupt on --corrupt-chance 50 --corrupt-ber 5000
🖥️
🌐
RST ⚡

Tears the TCP connection down by force

Connection

Set TCP RST forced reset

Sets the RST flag on TCP packets so the connection is torn down immediately. The receiving side treats it as an abnormal close. It has no effect on UDP. The default probability is 0%, so just switching it on does nothing — raise reset-chance or press the RST next packet button.

ParameterMeaningDefaultRange
reset-chanceRST injection probability0%0–100%
reset-nextRST the very next packet (button)—Fires once per click
Use it when — you want to test the client's reconnect handling at exactly the moment you choose, as if the TCP server process had suddenly died: use the RST next packet button.
clumsy.exe --filter "tcp and (tcp.DstPort==9000 or tcp.SrcPort==9000)" --reset on --reset-chance 5.0
🖥️
🌐

Slows down as it squeezes through a narrow section

Connection

Bandwidth bandwidth cap

Limits throughput (KB/s). Packets over the limit are not dropped but queued and sent later, in order. Once the queue passes 2,000 packets it starts dropping, and 0 holds every packet, which effectively blocks traffic.

ParameterMeaningDefaultRange
bandwidth-bandwidthBandwidth limit10 KB/s0–99999 KB/s
Use it when — reproducing slow mobile links or congested networks. It keeps the packets and only lowers the speed, so it suits TCP flow-control and retransmission tests better than Drop.
⚠️

The token bucket starts full, at 64 KB or limit × 2 seconds, whichever is larger. So in a short test it can look as if "the limit isn't kicking in" at first — that is normal.

clumsy.exe --filter "udp and outbound" --bandwidth on --bandwidth-bandwidth 500

How people actually use it

🎮 Reproduce ping to an overseas game server ▸Lag

Situation — the game server is overseas and always adds 150 ms of delay; you want to reproduce that ahead of time.

FilterLag

clumsy.exe --filter "udp and outbound" --lag on --lag-time 150

Situation — like Wi-Fi with a weak signal: latency jumps around and a packet goes missing now and then.

clumsy.exe --filter "udp and outbound" --jitter on --jitter-min 30 --jitter-max 200 --drop on --drop-chance 3.0

Situation — packets disappear back to back for a short stretch, like in a subway tunnel. Drop alone spreads the losses out and doesn't give you this feel.

🔌 Test reconnect logic ▸Blackout / TCP RST

Situation — you want to confirm that the client's reconnect code works correctly.

🤖 CI/CD automated testing ▸Scenario file

Situation — you want your build pipeline to run automated tests while stepping through different network conditions.

The simplest way is to define the whole flow in a single scenario file: an array that says "at second N, change to these values".

[
  { "at": 0,  "lag": true, "lag-time": 20 },
  { "at": 30, "lag-time": 200, "jitter": true, "jitter-min": 50, "jitter-max": 300,
              "drop": true, "drop-chance": 5.0 },
  { "at": 60, "lag-time": 500, "drop-chance": 15.0 }
]
clumsy.exe --filter "udp and outbound" --scenario ci_scenario.json --timeout 90

What to check — keep just the scenario file under version control and anyone on the QA team can reproduce the exact same conditions. Switching conditions live over the REST API or the Named Pipe is covered in the Automation section.

🧪 Packet tampering / fuzz testing ▸Tamper

Situation — you want to confirm that the server handles errors correctly when a game packet's header or sequence number is damaged.

GoalPositionChance
Damage sequence numbers (hit the header)0 (Front)5.0%
Unpredictable damage (fuzzing)3 (Random)10.0%

What to check — most game UDP packets keep their header at the front, so damaging the Front position lets you verify how the server handles a wrong packet type or sequence number. Random is closer to fuzzing: hunting for unexpected parse errors and crashes.

clumsy.exe --filter "udp and outbound" --tamper on --tamper-chance 5.0 --tamper-position 0 --tamper-checksum on
🔁 Test UDP duplicate handling ▸Duplicate

Situation — when network gear retransmits and the same packet arrives twice, you want to confirm that the server correctly ignores the duplicate.

FilterDuplicate
udp and outboundON, Count=2, Chance=20.0%

What to check — one in five packets is sent together with a copy. Check the server logs to see that it processes each duplicate only once (by sequence number or similar).

clumsy.exe --filter "udp and outbound" --duplicate on --duplicate-count 2 --duplicate-chance 20.0

CLI

Switching things on and off from the command line

The basic form is clumsy.exe --filter "expression" --module on --module-param value .... It behaves exactly the same as switching things on in the dashboard, and clumsy.exe --help shows the full list at any time. The tables below pick out the most-used options — for per-module parameters, see the tables in the Effects section.

Global options

OptionMeaning
--filter "expr"WinDivert filter. When given, capturing starts as soon as clumsy launches.
--process <name>Only filter the traffic of one process (e.g. game.exe).
--timeout <sec>Quit automatically after the given time. Handy in test scripts.
--profile <name>Load and apply a profile saved in profiles.json.
--scenario <file>Load a scenario JSON file and play it as capture starts.
--elevate onIf not running as Administrator, relaunch itself through UAC.
--pipe-name <name>Control pipe name (default clumsy). To run several instances at once, give each its own, together with its own --web-port.
--verbose on/offPer-packet detailed logging (for debugging; heavy performance cost).
--helpPrint every option. It is generated from the code, down to each module parameter's range and default, so it is always up to date.
--versionPrint the version.
🧭

Typos don't slip through silently. If there is an unknown option (--lag-ms, --delay) or an unusable value (letters where a number goes, a distribution name that doesn't exist), clumsy starts nothing, tells you the correct name and exits. A number outside its range is pulled back into range, with a warning that shows the value actually applied. Switches always take a value, as in --lag on, and on/off and true/false are case-insensitive.

Exit codes

CodeMeaning
0Clean exit (--timeout reached, Ctrl+C, POST /api/quit)
2Command-line error: unknown option, unusable value, or a --profile / --scenario that could not be loaded. Nothing is started.
3--filter (capture) or --replay-in (pcap replay) was given but could not start (no Administrator rights, filter syntax error, missing file and so on). clumsy exits right away instead of waiting.
4Clash with another running clumsy: its web port (--web-port) or pipe name (--pipe-name) is taken, or the filter overlaps packets another instance is already capturing. Only the newly launched one exits; the existing instance keeps running.

Common module pattern

PatternMeaning
--<module> on/offEnable/disable a module. e.g. --lag on
--<module>-<param> <value>Set a parameter. e.g. --lag-time 150, --drop-chance 5.0
--<module>-inbound / -outbound on/offShared by every module. Which direction to apply it to, receive and/or send (both ON by default)

Logging · statistics · automation helpers

--stats-interval <sec>Stats log interval (default 1 second).

# 100 ms delay + 3% drop on game-server UDP (port 7777)
clumsy.exe --filter "udp and (udp.DstPort==7777 or udp.SrcPort==7777)" --lag on --lag-time 100 --drop on --drop-chance 3.0

# Run for 30 seconds, then quit automatically
clumsy.exe --filter "udp and outbound" --lag on --lag-time 200 --timeout 30

# 60-second test that logs statistics to CSV
clumsy.exe --filter "udp and outbound" --drop on --drop-chance 5.0 --stats-log result.csv --timeout 60

# Fully headless run with no dashboard (for servers/containers)
clumsy.exe --filter "udp and outbound" --drop on --drop-chance 5.0 --web off --timeout 30

Every option is listed in clumsy.exe --help and in the manual that ships with the project (manual_en.md).

Automation

Remote control with the REST API

Everything the dashboard does when you click is, in the end, a REST API call. CI pipelines, automation scripts and other programs can control clumsy in exactly the same way. With the default settings (listening on 127.0.0.1 only), no authentication is needed. If you pass --web-token, or open it on an outside address with --web-bind, you need the X-Clumsy-Token header or ?token= (without --web-token, a random token is generated and appended to the dashboard address in the banner).

EndpointMeaning
GET/api/docsDescription, example body and API rules for every endpoint (start here)
GET/llms.txtUsage guide for AI agents. The Korean version is /llms_kr.txt
GET/api/healthLiveness check (no auth needed, for CI health checks)
GET/api/statusCapture state, filter, last message
GET/api/modulesFull state of every module + parameters + form metadata
GET/api/statsLive statistics (captured/sent/buffers/latency percentiles)
GET/api/streamServer-Sent Events, pushes stats every 200 ms
GET/metricsPrometheus text exposition format (no auth needed)
POST/api/filterSet the filter and start capturing
POST/api/stopStop capturing
POST/api/modules/{name}Enable a module / change its parameters
POST/api/applySet several modules at once, without saving
POST/api/scenario/loadinlineLoad the step array in the body {"scenario":[...]} without a file
POST/api/scenario/startReplay the loaded scenario from the beginning (it also plays automatically whenever a capture starts)
POST/api/quitStop capturing and shut clumsy down
📬

Read the whole response. Every response is JSON whose "status" is "ok" or "error". Even with ok, the request may not have gone through exactly as sent, and when that happens the response tells you — warnings (values that were out of range and adjusted, or refused), unknownKeys (keys no module has), params (the values actually applied), capturing (false means the setting is only stored and isn't acting on traffic yet). If none of the requested keys could be applied, the reply is a 400 error, and an unknown path or wrong method also gets a JSON answer telling you what to use instead.

curl examples

# Start capturing
curl -X POST http://127.0.0.1:8080/api/filter -H "Content-Type: application/json" -d "{\"filter\":\"udp and outbound\"}"

# Turn lag on and set the delay to 200 ms
curl -X POST http://127.0.0.1:8080/api/modules/lag -H "Content-Type: application/json" -d "{\"enabled\":true,\"lag-time\":200}"

# Set several modules at once
curl -X POST http://127.0.0.1:8080/api/apply -H "Content-Type: application/json" -d "{\"lag\":true,\"lag-time\":200,\"drop\":true,\"drop-chance\":5.0}"

# Stop capturing, then check the statistics
curl -X POST http://127.0.0.1:8080/api/stop
curl http://127.0.0.1:8080/api/stats

Subscribing to the live stream from Python

import requests, json

with requests.get("http://127.0.0.1:8080/api/stream", stream=True) as r:
    for line in r.iter_lines(decode_unicode=True):
        if line and line.startswith("data: "):
            stats = json.loads(line[6:])
            print(stats["captured"], stats["sent"])
🔧

There is also a Named Pipe API. On Windows you exchange one JSON request for one JSON response over \\.\pipe\clumsy. It shares exactly the same internal handling code (controlapi.cpp) as REST, so the two can never behave differently. If you already have automation scripts built on the Named Pipe, they keep working without changes.

AI agents

Describe it in plain words and an AI runs it for you

clumsy is built to be driven not only by people but also by AI coding agents (Claude Code, Codex, Cursor, Copilot agents and so on). Describe what you want — "150 ms of latency and 5% loss for 60 seconds" — and the agent turns it into commands or REST calls, runs the test, reads the statistics, and puts the network back to normal when it is done. You don't need to memorize any option names.

Just tell it these four things

  1. Where clumsy is

    The path to clumsy.exe. e.g. C:\tools\clumsy\clumsy.exe

  2. Which traffic

    The port or server address the target program uses, and whether it is TCP or UDP. Without this the agent has to guess a filter, and a broad filter degrades all communication on the PC (including the agent's own connection).

  3. What condition you want

    Plain words are enough: "150 ms latency and 5% loss", "a bad 3G connection", "a 5-second outage every 30 seconds".

  4. For how long

    The agent passes this as --timeout. It is the safety net that guarantees the network recovers even if something goes wrong.

🛡️

There is one thing only you can do. Open the terminal the agent runs in as Administrator (on Linux, sudo or CAP_NET_ADMIN). Intercepting packets needs that right, and an agent cannot elevate itself. Without it, clumsy says so and exits with code 3.

Troubleshooting

Frequently asked questions

I get an error saying Administrator rights are required

clumsy has to load a network driver (WinDivert) to intercept packets. Restart your console (Command Prompt/PowerShell) as Administrator. If doing that by hand every time is a chore, add --elevate on and clumsy will bring up the UAC prompt for you.

I entered a filter and pressed Start, but nothing happens

The two most common causes: ① for a localhost test, check whether the outbound condition is missing (inbound and loopback does not work). ② You turned the module on, but check that its Inbound/Outbound checkboxes aren't set opposite to the actual traffic direction.

A second clumsy quits with exit code 4

Several clumsy instances can run at once, but they cannot share a web port or a pipe name, and their filters cannot match the same packets. When one of those clashes, the newly launched one prints the reason and exits with code 4; the existing instance keeps running. Give each instance its own --web-port and --pipe-name (e.g. --web-port 8081 --pipe-name client1). If the message says filter overlaps, narrow the filter so it only covers this instance's client, for example (udp.SrcPort == 50001 and udp.DstPort == 7777) or (udp.SrcPort == 7777 and udp.DstPort == 50001). If you only wanted one clumsy, keep using the existing one from the dashboard or the REST API, or shut it down with POST /api/quit (or Ctrl+C in its console window) and launch again.

I passed an option and it quit right away with "unknown option"

The option name is wrong or the value is in an unusable form. clumsy doesn't silently ignore bad options; it stops before starting anything (exit code 2) and tells you the correct name. Switch to the name shown in the message or look it up in clumsy.exe --help. Switches need a value: --lag on, not --lag.

I asked an AI agent and it says it has no permission

The terminal the agent runs in isn't elevated. Restart the terminal (or the IDE that launched the agent) as Administrator and ask again. An agent cannot elevate itself. See the AI agents section for details.

I set a low Bandwidth limit, but at first it doesn't seem to apply

That's normal. The bandwidth cap is a token bucket, and it starts full, at 64 KB or limit × 2 seconds, whichever is larger. So in a short test the early traffic looks as if it went straight through — run the test a bit longer (or with more data).

The dashboard won't open in my browser

Check that you typed the address from the banner printed in the console exactly (default http://127.0.0.1:8080/). If another program is already using port 8080, pick a different port, e.g. --web-port 9090.

I want to control this clumsy instance remotely from another PC

Run it with --web-bind 0.0.0.0 --web-token your-token and it can be reached from outside. When bound to an outside address, a token is mandatory, so every request must carry the X-Clumsy-Token header or a ?token= query string. Only do this on a trusted test network.

I switched on Set TCP RST but nothing happens

Check the probability first. reset-chance defaults to 0%, so --reset on alone touches no packets — raise it, as in --reset-chance 5.0, or press the dashboard's RST next packet button. Also, the Reset module is TCP only and has no effect on UDP traffic. Make sure your filter includes a tcp condition and that the target service really uses TCP.
