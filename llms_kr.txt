# clumsy

> clumsy는 실제 네트워크 트래픽을 일부러 나쁘게 만드는 도구입니다. 지연, 지터,
> 패킷 손실, 연결 두절, 순서 뒤섞임, 손상, 대역폭 제한을 걸어 애플리케이션이
> 나쁜 연결에서 어떻게 동작하는지 확인할 수 있습니다. 시스템 전체의 실제 패킷을
> 가로채므로(Windows는 WinDivert, Linux는 NFQUEUE) 프록시도, 대상 애플리케이션
> 수정도 필요 없습니다. 명령줄 옵션과 로컬 REST API로 제어합니다.
> 이 파일은 AI 에이전트와 스크립트를 위한 사용 가이드입니다.

이 문서는 llms.txt(영문)의 한국어판이며 내용은 같습니다. 옵션 이름, API 경로,
clumsy가 출력하는 메시지는 번역하지 않고 원문 그대로 씁니다.

다음 세 가지는 실행 중인 코드에서 생성되므로 항상 최신입니다. clumsy나 비슷한
도구(tc/netem, Network Link Conditioner, toxiproxy)에 대해 기억하고 있는 내용보다
이것을 우선하세요. 옵션 이름이 서로 다릅니다.

- `clumsy --help`      모든 옵션, 모든 모듈 파라미터의 범위와 기본값, 종료 코드.
                       권한이 필요 없습니다.
- `GET /api/docs`      모든 REST 엔드포인트와 예시 본문.
- `GET /api/modules`   모든 모듈의 설명, 파라미터(key, type, min, max, options),
                       현재 값.


## 흔한 실수를 막는 규칙

1. 캡처가 실행 중이어야 트래픽에 작용합니다. 캡처는 명령줄의 `--filter` 또는
   `POST /api/filter`로 시작합니다. 필터 없이 모듈만 켜면 아무 일도 일어나지
   않고, 오류도 나지 않습니다.
2. 모든 옵션은 `--키 값` 쌍입니다. 스위치도 값을 씁니다. `--lag on`이 맞고,
   `--lag`만 쓰면 안 됩니다.
3. 모듈은 켜는 것과 설정하는 것을 둘 다 해야 합니다: `--lag on --lag-time 100`.
   `--lag-time 100`만 쓰면 꺼져 있는 모듈에 값만 들어갑니다.
4. 확률은 0~100의 퍼센트입니다. `--drop-chance 5`는 5%입니다.
   시간은 밀리초, 대역폭은 초당 킬로바이트입니다.
5. 캡처에는 권한이 필요합니다. Windows는 관리자 콘솔, Linux는 CAP_NET_ADMIN
   (또는 sudo). `GET /api/status`의 `"admin"`을 확인하세요. false면 사용자에게
   터미널을 관리자 권한으로 다시 열어 달라고 알리세요. 권한 없는 셸에서는
   해결할 수 없습니다.
6. clumsy를 실행할 때는 항상 `--timeout <초>`를 주세요. 안전장치입니다. 끄는 것을
   잊은 clumsy는 사용자의 네트워크를 계속 망가뜨립니다.
7. 필터는 좁게 잡으세요. 테스트 대상 애플리케이션의 포트나 주소로 한정합니다.
   넓은 필터(`true`, `tcp`, `outbound`)는 사용자의 브라우저, 에이전트 자신의 API
   연결, clumsy의 제어 포트까지 건드립니다.
8. clumsy는 멈추라고 할 때까지 실행됩니다. 백그라운드로 띄운 뒤
   `GET /api/health`가 응답할 때까지 폴링하세요.
9. clumsy는 여러 개를 동시에 실행할 수 있습니다. 예를 들어 테스트할 클라이언트마다
   하나씩 띄워 각자 다른 조건을 줄 수 있습니다(절차 C). 인스턴스마다 `--web-port`와
   `--pipe-name`이 달라야 하고 리눅스에서는 `--queue-num`도 달라야 합니다. 이미 쓰이는
   값이면 새 인스턴스가 종료 코드 4로 끝납니다. 직접 띄우지 않은 포트에서 응답하는
   clumsy는 당신 것이 아니니 건드리지 마세요.
10. 응답을 끝까지 읽으세요. REST 응답은 `"status":"ok"`이면서도
    `"unknownKeys"`(어떤 모듈에도 없는 키)나 `"warnings"`(범위 안으로 조정됐거나
    적용되지 않은 값)를 담고 있을 수 있습니다. `"params"`는 실제로 적용된 값이고,
    `"capturing": false`는 설정은 저장됐지만 아직 아무 트래픽에도 작용하지 않는다는
    뜻입니다. 쓸 수 있는 키가 하나도 없는 요청은 오류(400)입니다.
11. 끝나면 `POST /api/quit`로 종료하고, 사용자에게 네트워크가 정상으로 돌아왔다고
    알리세요.


## 모듈 고르기

모듈은 캡처된 패킷마다 아래 순서로 적용됩니다. 처음에는 모두 꺼져 있습니다.
모든 모듈은 `<모듈>-inbound`, `<모듈>-outbound`(on|off, 기본 둘 다 on)로 방향을
한정할 수 있습니다.

| 재현하려는 상황 | 모듈 | 파라미터 (범위, 기본값) |
|---|---|---|
| 일정한 추가 지연 | lag | lag-time 0..15000 ms (50) |
| 들쭉날쭉한 지연 | jitter | jitter-min, jitter-max 0..5000 ms (20, 100); jitter-dist uniform/normal/pareto (uniform) |
| 고르게 퍼진 패킷 손실 | drop | drop-chance 0..100 % (10) |
| 몰아서 오는 손실 | burstloss | burstloss-good, burstloss-bad: 좋은/나쁜 상태에서의 손실 % (2, 80); burstloss-gb, burstloss-bg: 패킷마다 좋음->나쁨, 나쁨->좋음으로 바뀔 확률 % (5, 20) |
| 반복되는 완전 두절 | blackout | blackout-duration 100..60000 ms (3000); blackout-gap 두절 사이의 정상 구간 1000..300000 ms (15000); blackout-trigger: 액션, 지금 두절 시작/해제 |
| 끊김: 붙잡았다가 한꺼번에 방출 | throttle | throttle-frame 0..1000 ms (30); throttle-chance 0..100 % (10); throttle-drop on/off: 방출 대신 버림 (off) |
| 패킷 중복 | duplicate | duplicate-count 2..50 개 (2); duplicate-chance 0..100 % (10) |
| 순서가 뒤바뀐 도착 | ood | ood-chance 0..100 % (10); ood-buffer 2..50 패킷 (5); ood-delay 10..2000 ms (200) |
| 애플리케이션 데이터 손상 | tamper | tamper-chance 0..100 % (10); tamper-position 0=앞 1=가운데 2=뒤 3=무작위 (1); tamper-checksum on/off: 손상이 앱까지 도달하도록 체크섬 재계산 (on) |
| 비트 에러 (잡음 많은 무선) | corrupt | corrupt-chance 패킷의 0..100 % (10); corrupt-ber 백만 비트당 뒤집을 비트 수 0..1000000 (100); corrupt-checksum on/off (on) |
| TCP 연결 강제 종료 | reset | reset-chance 0..100 % (0); reset-next: 액션, 다음 패킷을 리셋 |
| 느린 회선 | bandwidth | bandwidth-bandwidth 0..99999 KB/s (10) |

명령줄에서는 각 키 앞에 `--`를 붙입니다. REST 본문과 시나리오 파일에서는 같은
키를 대시 없이 씁니다.

자주 쓰는 조합:

| 상황 | 설정 |
|---|---|
| 모바일 4G | lag 80 ms, drop 2 %, throttle 10 % |
| 모바일 3G | lag 150 ms, drop 5 %, bandwidth 500 KB/s |
| 위성 | lag 500 ms, drop 1 % |
| 불안정한 Wi-Fi | jitter 20..200 ms, burstloss good 2 / bad 80 |
| 터널 / 엘리베이터 | blackout: 정상 30000 ms마다 3000 ms 두절 |

값에 대한 참고:

- 모듈은 겹쳐서 작용합니다. 켜진 모듈은 앞 모듈이 통과시킨 패킷에 작용하므로,
  `drop` 5 %에 `burstloss`를 더하면 각각보다 더 많이 잃습니다.
- blackout은 `blackout-gap` ms의 정상 구간과 `blackout-duration` ms의 두절을
  번갈아 반복합니다. "20초마다 2초 두절"은 duration 2000, gap 18000입니다.
- burstloss 기본값은 약 20 %의 시간을 나쁜 상태로 보내며, 평균 손실은 18 % 정도
  입니다. 더 약하게 하려면 `burstloss-gb`(몰림이 시작되는 빈도)나
  `burstloss-bad`(몰림 중의 손실률)를 낮추세요.
- bandwidth는 초당 킬로바이트(1 KB = 1024바이트)이며 킬로비트가 아닙니다.
  제한값 0은 완전 차단입니다. 큐에서 하나도 내보내지 않습니다.
- 액션 `blackout-trigger`와 `reset-next`는 해당 모듈이 이미 켜져 있고 캡처가
  실행 중일 때만 동작하며, 그 밖에는 무시됩니다. 모듈을 켜고 캡처를 시작한 뒤,
  별도 요청으로 액션을 보내세요.


## 필터 작성

필터는 clumsy가 어떤 패킷을 건드릴지 정합니다. 나머지는 그대로 통과합니다.
문법은 WinDivert 필터 언어입니다.

    udp and udp.DstPort == 7777                          UDP 포트 하나, 그 포트로 가는 방향
    udp and (udp.DstPort == 7777 or udp.SrcPort == 7777) 그 포트의 양방향
    tcp and (tcp.DstPort == 443 or tcp.SrcPort == 443)   모든 HTTPS
    ip.DstAddr == 10.0.0.5 or ip.SrcAddr == 10.0.0.5     원격 호스트 하나
    outbound and udp                                     이 PC에서 나가는 모든 UDP
    outbound and loopback                                localhost끼리의 트래픽

- 구성 요소: `and` `or` `not`과 괄호; `inbound` `outbound` `loopback`;
  `tcp` `udp` `icmp` `ip` `ipv6`; `ip.SrcAddr` `ip.DstAddr` `tcp.SrcPort`
  `tcp.DstPort` `udp.SrcPort` `udp.DstPort`; `==` `!=` `<` `>` `<=` `>=`.
- 루프백 트래픽은 `outbound`로만 매치됩니다. `outbound and loopback`으로 쓰고,
  `inbound and loopback`은 쓰지 마세요.
- 무언가를 제외하려면 긍정 조건을 `not ( ... )`로 감싸세요. `tcp.DstPort != 8080`을
  그대로 쓰면 TCP가 아닌 모든 패킷에서 거짓이 되어, UDP 전체가 조용히 매치에서
  빠집니다.
- clumsy 자신의 REST API는 127.0.0.1의 TCP이고, `--web-port`로 바꾸지 않았다면
  8080 포트입니다. 필터가 루프백 TCP를 매치한다면 그 포트를 제외하세요. 그러지
  않으면 손실이 클 때 API에 접근할 수 없게 됩니다(8080 자리에 실제 포트를 넣으세요):
  `outbound and loopback and not (tcp.DstPort == 8080 or tcp.SrcPort == 8080)`
- 포트 하나만 검사하면(`udp.DstPort == 7777`) 그 포트로 가는 패킷만 매치됩니다.
  응답까지 건드리려면 위 두 번째 예시처럼 `DstPort`와 `SrcPort`를 함께 검사하세요.
- `--process game.exe`(또는 `POST /api/filter`의 `"process"`)는 그 프로세스가 지금
  열고 있는 포트로 캡처를 추가로 한정합니다.
- `GET /api/presets`는 미리 만들어 둔 이름 붙은 필터(게임 엔진 등)를 돌려줍니다.
- 문법이 틀린 필터는 메시지와 함께 시작에 실패합니다. 고쳐서 다시 시도하세요.


## 절차 A: 시간을 정한 1회 실행 (명령줄만)

테스트 내내 조건이 그대로일 때 씁니다.

    clumsy --filter "udp and udp.DstPort == 7777" --lag on --lag-time 150 --drop on --drop-chance 5 --timeout 60 --stats-log stats.csv --report-out report.html

60초 뒤 종료 코드 0으로 스스로 끝나고, `stats.csv`(초당 한 줄)와 `report.html`이
남습니다. 대상 애플리케이션을 직접 조작한다면 백그라운드로, 테스트가 다른 곳에서
돈다면 포그라운드로 실행하세요. 출력 파일은 캡처가 실행 중일 때만 기록됩니다.
종료 코드 3 뒤에 파일이 없는 것은 별개의 문제가 아닙니다.

이 예시는 7777 포트로 가는 패킷만 건드립니다. 응답까지 건드리려면 위 절의 양방향
필터를 쓰세요.

종료 코드:

    0  정상 종료 (--timeout 도달, Ctrl+C, POST /api/quit)
    2  명령줄 오류: 모르는 옵션, 쓸 수 없는 값, 불러올 수 없는 --profile /
       --scenario. 아무것도 시작하지 않았습니다. stderr 메시지가 해당 옵션과
       올바른 이름을 알려줍니다.
    3  캡처(--filter)나 재생(--replay-in)을 시작하지 못함: 권한 없음 또는 필터
       문법 오류. 아무 트래픽에도 작용하지 않습니다.
    4  실행 중인 다른 clumsy와 충돌: --web-port나 --pipe-name이 이미 쓰이고 있거나,
       다른 인스턴스가 이미 캡처 중인 패킷과 필터가 겹칩니다. 메시지가 그
       인스턴스(pid, web, pipe, filter)를 알려줍니다.


## 절차 B: 한 번 띄워 놓고 REST로 조건 변경

테스트 중에 조건이 바뀌거나, 실행 중에 통계를 읽어야 할 때 씁니다. 기본 주소는
`http://127.0.0.1:8080`이며 `--web-port`를 줬다면 그 포트입니다.

1. 필터 없이, 넉넉한 타임아웃으로 백그라운드 실행:

       clumsy --timeout 600 --stats-console 0

2. `GET /api/health`가 `{"status":"ok",...}`를 돌려줄 때까지 기다립니다.
3. `GET /api/status` - `"admin"`이 false면 여기서 멈추고 사용자에게 알립니다.
4. 모듈을 요청 하나로 설정:

       POST /api/apply
       {"lag":true,"lag-time":150,"drop":true,"drop-chance":5}

   응답이 지금 적용된 값을 돌려줍니다:
   `{"status":"ok","applied":4,"capturing":false,"params":{"lag":"true","lag-time":"150","drop":"true","drop-chance":"5.0"}}`

5. 캡처 시작:

       POST /api/filter
       {"filter":"udp and udp.DstPort == 7777"}

6. 테스트를 진행합니다. `POST /api/apply`나 `POST /api/modules/{name}`으로 언제든
   조건을 바꿀 수 있고, 즉시 반영됩니다.
7. 검증하고(다음 절), 리포트가 필요하면 `GET /api/report`를 받습니다.
8. `POST /api/stop`은 네트워크를 정상으로 돌리고 clumsy는 계속 띄워 둡니다.
   `POST /api/quit`은 clumsy를 종료합니다.

curl (bash):

    curl -s http://127.0.0.1:8080/api/status
    curl -s -X POST http://127.0.0.1:8080/api/apply -H "Content-Type: application/json" -d '{"lag":true,"lag-time":150}'
    curl -s -X POST http://127.0.0.1:8080/api/filter -H "Content-Type: application/json" -d '{"filter":"udp and udp.DstPort == 7777"}'
    curl -s -X POST http://127.0.0.1:8080/api/quit

PowerShell (Windows PowerShell 5.1에서 `curl`은 Invoke-WebRequest의 별칭이라 인수가
다릅니다. 대신 아래를 쓰세요):

    Invoke-RestMethod http://127.0.0.1:8080/api/status
    Invoke-RestMethod -Method Post http://127.0.0.1:8080/api/apply -ContentType application/json -Body '{"lag":true,"lag-time":150}'
    Invoke-RestMethod -Method Post http://127.0.0.1:8080/api/filter -ContentType application/json -Body '{"filter":"udp and udp.DstPort == 7777"}'
    Invoke-RestMethod -Method Post http://127.0.0.1:8080/api/quit

PowerShell에서 백그라운드로 띄우기:

    Start-Process clumsy.exe -ArgumentList '--timeout','600','--stats-console','0' -WindowStyle Hidden

REST 규칙:

- GET과 POST만 있습니다. POST 본문은 JSON 객체입니다. 조회는 GET, 동작은 POST이며,
  메서드나 경로가 틀리면 그 사실을 알려주는 JSON 오류가 옵니다.
- 모든 JSON 응답에는 `"status"`가 있습니다: `"ok"` 또는 `"error"`(+`"message"`).
- 불리언은 `true`/`false`, `"on"`/`"off"`, `1`/`0` 모두 됩니다.
- 토큰은 clumsy를 `--web-token`이나 루프백이 아닌 `--web-bind`로 실행했을 때만
  필요합니다. `X-Clumsy-Token` 헤더로 보냅니다.
- `GET /api/stream`은 끝나지 않는 Server-Sent Events 스트림입니다. 스크립트에서는
  `GET /api/stats`를 폴링하세요.


## 절차 C: 한 PC의 클라이언트 여러 개

한 PC에서 클라이언트 여러 개(서버도 같은 PC일 수 있음)를 돌리면서, 그 전부나 일부를
같은 조건으로, 또는 클라이언트마다 다른 조건으로 망가뜨릴 때 씁니다. 서버가 같은 PC에
있든 다른 PC에 있든 방법은 같습니다. clumsy는 클라이언트가 있는 PC에서 실행합니다.

먼저 구성을 정하세요.

- 모든 클라이언트, 또는 고른 몇 개에 같은 조건: clumsy 하나에 그 클라이언트들을 고르는
  필터를 줍니다.
- 클라이언트마다 다른 조건: 조건 묶음마다 clumsy를 하나씩 띄웁니다. 같은 조건을 받는
  클라이언트들은 인스턴스를 공유합니다. 인스턴스마다 `--web-port`, `--pipe-name`,
  출력 파일 이름을 따로 주고, 리눅스에서는 `--queue-num`도 따로 줍니다.

클라이언트마다 로컬 포트를 확인하세요. 클라이언트는 보통 접속할 때마다 임의의 포트를
받으므로 접속한 뒤에 확인합니다(클라이언트가 고정 포트를 쓰게 하면 더 간단합니다).

    Windows   Get-NetUDPEndpoint -OwningProcess <pid>
              Get-NetTCPConnection -OwningProcess <pid> -State Established
    Linux     ss -unap | grep <pid>        ss -tnap | grep <pid>

필터 예시입니다. 서버 포트가 7777이라고 가정합니다(TCP면 `udp` 대신 `tcp`).

    모든 클라이언트      udp.DstPort == 7777 or udp.SrcPort == 7777
    클라이언트 하나      (udp.SrcPort == 50001 and udp.DstPort == 7777) or (udp.SrcPort == 7777 and udp.DstPort == 50001)
    클라이언트 둘        (udp.SrcPort == 50001 and udp.DstPort == 7777) or (udp.SrcPort == 7777 and udp.DstPort == 50001) or (udp.SrcPort == 50002 and udp.DstPort == 7777) or (udp.SrcPort == 7777 and udp.DstPort == 50002)
    원격 서버            ip.DstAddr == 10.0.0.5 or ip.SrcAddr == 10.0.0.5  (그 서버의 모든 클라이언트)

- 위처럼 클라이언트 흐름의 포트 두 개를 모두 적으세요. `udp.SrcPort == 50001 or
  udp.DstPort == 50001`만 쓰면 50001에서 50002로 가는 패킷도 매치되므로, 50002용
  인스턴스와 겹쳐서 거부됩니다.
- 필터는 위 예시처럼 AND로만 묶은 그룹들을 OR로 잇는 형태로 쓰세요. 리눅스의
  `--auto-iptables`는 그룹마다 정확한 iptables 규칙을 만듭니다. `udp and (...)` 안에
  들어간 그룹은 나눌 수 없어 규칙이 UDP 전체로 넓어지고, 다른 인스턴스와 모두 겹칩니다.
- 이 필터들은 localhost 트래픽에도 매치됩니다(나가는 방향으로 한 번 잡힘). 그래서 서버가
  같은 PC에 있어도 `loopback` 조건이 필요 없고, clumsy 자신의 REST 포트도 건드리지 않습니다.
- lag는 필터가 매치하는 방향마다 더해집니다. `--lag-time 100`이면 왕복 시간이 약 200ms
  늘어납니다. 한 방향만 지연시키려면 해당 그룹만 남기세요. 예를 들어 클라이언트에서
  서버로 가는 방향만이면 `(udp.SrcPort == 50001 and udp.DstPort == 7777)`입니다.
  localhost 패킷은 모두 outbound로 잡히므로 `<모듈>-inbound` / `-outbound` 스위치로는
  방향을 나눌 수 없고, 포트 순서로 나눠야 합니다.

조건이 다른 클라이언트 두 개(PowerShell. 리눅스에서는 같은 옵션을 `sudo`로 실행하고
`--auto-iptables on --queue-num 1`과 `2`를 더합니다):

    Start-Process clumsy.exe -WindowStyle Hidden -ArgumentList '--web-port','8081','--pipe-name','client1','--timeout','600','--stats-console','0','--filter','"(udp.SrcPort == 50001 and udp.DstPort == 7777) or (udp.SrcPort == 7777 and udp.DstPort == 50001)"','--lag','on','--lag-time','150'
    Start-Process clumsy.exe -WindowStyle Hidden -ArgumentList '--web-port','8082','--pipe-name','client2','--timeout','600','--stats-console','0','--filter','"(udp.SrcPort == 50002 and udp.DstPort == 7777) or (udp.SrcPort == 7777 and udp.DstPort == 50002)"','--drop','on','--drop-chance','10'

그다음은 각자의 포트에서 절차 B와 똑같이 제어하고(`http://127.0.0.1:8081/api/...`,
`http://127.0.0.1:8082/api/...`), 끝나면 각각 `POST /api/quit`을 보내세요.

실행 중인 다른 인스턴스가 이미 캡처하는 패킷과 겹칠 수 있는 필터는 시작이 거부됩니다.
명령줄에서는 종료 코드 4, `POST /api/filter`에서는 HTTP 409입니다. 메시지가 상대
인스턴스와, 양쪽에 모두 매치되는 예시 패킷을 알려줍니다.

    filter overlaps the clumsy with pid 4120 (web http://127.0.0.1:8081/, pipe \\.\pipe\client1)
    capturing "...": both would match udp, src port 50001, dst port 7777. ...

그 예시 패킷이 더는 매치되지 않도록 필터를 좁히거나, 그 인스턴스가 당신이 남겨 둔
것이면 끄세요. 클라이언트가 다시 접속하면 보통 포트가 바뀝니다. 새 포트를 다시 확인해
`POST /api/filter`로 보내세요.


## 동작하는지 검증하기

캡처 중의 `GET /api/stats`:

    {"status":"ok","capturing":true,"elapsedMs":12040,"captured":5321,"sent":5108,
     "modules":{"lag":{"enabled":true,"affected":5321},"drop":{"enabled":true,"affected":213}, ...},
     "latency":{"count":5108,"p50":150,"p95":151,"p99":152, ...}, ...}

- `capturing`이 false: 캡처가 없습니다. 필터를 줘서 시작하세요.
- `captured`가 계속 0: 필터에 맞는 트래픽이 없습니다. 포트, 프로토콜, 방향을
  확인하고, 애플리케이션이 실제로 보내고 있는지 확인하세요.
- `captured`는 늘지만 어떤 모듈의 `affected`가 0: 그 모듈이 꺼져 있거나, 확률이
  0이거나, 방향 스위치가 그 트래픽을 제외하고 있습니다.
- `latency`는 lag와 jitter가 실제로 더한 지연입니다.

진짜 확인은 사용자가 보는 결과(애플리케이션이 느려지고, 재시도하고, 끊기는 것)
입니다. 카운터는 패킷을 건드렸다는 사실만 증명합니다.


## 시나리오: 시간에 따라 바뀌는 조건

시나리오는 스텝의 JSON 배열입니다. 각 스텝에는 트리거 하나와 `POST /api/apply`가
받는 키들이 들어갑니다. 캡처가 시작될 때 함께 재생됩니다.

    [
      {"at": 0,  "lag": true, "lag-time": 80},
      {"at": 20, "drop": true, "drop-chance": 5},
      {"at": 40, "blackout": true, "blackout-duration": 3000, "blackout-gap": 20000},
      {"at": 70, "lag": false, "drop": false, "blackout": false},
      {"when": "captured_count", "op": ">=", "value": 20000, "bandwidth": true, "bandwidth-bandwidth": 200},
      {"at": 90, "repeat": 30, "times": 5, "drop-chance": 10}
    ]

- `at`: 캡처 시작 후 경과 초.
- `when` + `op`(`>=` `>` `<=` `<` `==`) + `value`: 메트릭이 값을 넘을 때 실행.
  메트릭: `captured_count`, `sent_count`, `pps`, `elapsed_sec`, `lag_buf`,
  `jitter_buf`, `bandwidth_buf`, `affected:<모듈>`.
- `repeat`: N초마다 다시 실행. `times`: 횟수(없으면 무한).
- `_`로 시작하는 키는 무시되므로 `"_comment": "..."`를 써도 됩니다.
- `--scenario file.json`으로 불러오거나, 파일 없이:

      POST /api/scenario/loadinline
      {"scenario": [{"at":0,"lag":true,"lag-time":80},{"at":30,"lag":false}]}

  응답의 `"warnings"`가 모르는 키, 잘못된 값, 없는 메트릭을 알려줍니다. 캡처를
  시작하기 전에 고치세요.
- 스텝은 캡처 시작 시점부터 시간을 재고, 캡처 중에만 실행됩니다. 시나리오를 먼저
  로드한 다음 `POST /api/filter`를 보내면 함께 시작됩니다.


## 그 밖의 출력

- `--stats-log file.csv|file.json` + `--stats-interval <초>`: 시계열 통계.
- `--report-out report.html`(또는 `GET /api/report`): HTML 세션 리포트.
- `--pcap-out file.pcap`(또는 `POST /api/pcap/start`): Wireshark로 열 수 있는 덤프.
  `--pcap-stage pre|post|both`로 모듈 적용 전/후를 고릅니다.
- `GET /metrics`: Prometheus 텍스트 형식.
- 프로파일은 모듈 설정을 이름으로 저장합니다: `POST /api/profiles {"name":"x"}`,
  이후 `--profile x` 또는 `POST /api/profiles/x/apply`. 기본 제공 프로파일은 없습니다.


## 플랫폼별 참고

Windows
- 관리자 콘솔이 필요합니다. `--elevate on`은 사람이 수락해야 하는 UAC 창을 띄우고,
  권한이 올라간 clumsy는 새 콘솔 창에서 열리며 원래 프로세스는 0으로 끝납니다.
  출력이 사라지므로 이후는 REST로 따라가세요.
- 두 번째 제어 채널로 Named Pipe `\\.\pipe\clumsy`가 있습니다. `--pipe-name <이름>`을
  주면 `\\.\pipe\<이름>`입니다(JSON 요청 하나에 JSON 응답 하나, 예:
  `{"cmd":"get_status"}`, `{"cmd":"quit"}`). 네트워크를 쓰지 않으므로 필터가 REST
  포트를 막아버렸을 때도 응답합니다.

Linux
- CAP_NET_ADMIN이 필요합니다(sudo로 실행하거나, 권한을 부여해 주는 .deb 설치).
- `--auto-iptables on`을 붙이세요. 없으면 iptables NFQUEUE 규칙이 보내주는
  트래픽만 clumsy가 볼 수 있고, 그 규칙을 직접 관리해야 합니다.
- 필터 언어는 부분집합입니다: 위에 나열한 키워드, IPv4 주소만. 지원하지 않는
  항목은 시작할 때 거부됩니다.
- 제어 채널은 Named Pipe 대신 Unix 소켓입니다. 경로는 `/run/<이름>.sock`이고, 권한이
  없으면 `/tmp/<이름>.sock`입니다. `<이름>`은 `--pipe-name`(기본값 `clumsy`)이며,
  경로는 시작 배너에 출력됩니다.
- 여러 인스턴스를 띄우려면 `--queue-num`도 서로 달라야 합니다.
- WSL2에서는 WSL2 네트워크 네임스페이스 안의 트래픽만 보이고, Windows 호스트의
  애플리케이션은 보이지 않습니다.


## 문제가 생겼을 때

| 증상 | 원인과 해결 |
|---|---|
| 곧바로 종료 코드 2 | stderr를 읽으세요. 어느 옵션인지 나옵니다. `clumsy --help`로 확인. |
| 종료 코드 3, "needs Administrator rights" | 권한이 없습니다. 사용자에게 터미널을 관리자 권한으로 실행해 달라고 하세요. |
| 종료 코드 3, 필터 오류 | 필터 문법이 틀렸습니다. 단순하게 줄여 다시 시도하세요. |
| 종료 코드 4, "web port ... is in use" | 다른 clumsy나 프로그램이 그 포트를 씁니다. 비어 있는 `--web-port`를 주세요. |
| 종료 코드 4, "control pipe name is in use" | 다른 clumsy가 그 이름을 씁니다. 겹치지 않는 `--pipe-name`을 주세요. |
| 종료 코드 4 또는 HTTP 409, "filter overlaps" | 다른 인스턴스가 같은 패킷 일부를 캡처 중입니다. 필터를 좁히세요(절차 C). |
| REST 연결 거부 | 아직 안 떴거나(/api/health 폴링), `--web-port`가 다르거나, `--web off`입니다. |
| 되던 REST가 타임아웃 | 필터가 제어 포트를 건드리고 있습니다. `--timeout`을 기다리거나 Named Pipe로 `{"cmd":"quit"}`을 보내세요. 다음에는 그 포트를 제외하세요. |
| 모든 엔드포인트가 401 | 토큰이 설정돼 있습니다. `X-Clumsy-Token` 헤더를 보내세요. |
| "status":"ok"인데 변화가 없음 | 캡처가 없거나, 응답의 `unknownKeys` / `warnings`를 확인하세요. |
| PC 전체의 네트워크가 안 됨 | 필터가 너무 넓은데 손실이나 blackout이 큽니다. `POST /api/quit`, 또는 `--timeout`을 기다리세요. |
